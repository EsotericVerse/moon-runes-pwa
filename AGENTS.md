## Priority order

Security ≫ Portable > Loading = UI > Code is the **ordinary engineering default**, not a timeless priority queue or an unconditional ordering for every task. When a real authentication, authorization, privacy, data-integrity or other security boundary is implicated, its required checks remain hard acceptance constraints; this does **not** justify elevating unrelated security or deployment work above the requested UI, product or game task. Determine the effective priority from the current context, verified severity, time pressure, likely consequences, dependencies and the user's actual objective. Preserve a workable balance among the dimensions rather than maximizing one by default. When a genuine tradeoff cannot be resolved without sacrificing an important requirement, show the alternatives and let the user decide; do not silently decide solely from the default rank.

- **The framework is multi-variable, not one permanent bottom line.** Consider the specific object/domain, user intent, evidence, knowns and unknowns, time, risk, urgency, impact, dependencies, reversibility, resources and responsibility. - **Time is a decision dimension.** Compare decisions in their actual times and conditions: experience, available information, severity and consequences may change. Investigate the changed conditions before labeling a decision inconsistent or a user changeable.
- **Treat unknowns as explicit variables, not excuses or fabricated answers.** Start from verified known facts, derive only what follows from them, and keep unresolved assumptions marked as questions until evidence narrows them. - **Prefer stability with purposeful, bounded change.** Preserve a dependable baseline and adapt through small, justified improvements; neither freeze everything forever nor invent disruptive work to demonstrate progress. ## Adaptive diagnosis: question-driven, never stubborn

- **Do not fall in love with the first explanation.** An initial symptom or correlation is a hypothesis, not the root cause. Begin with the observed failure and trace its actual call path and dependencies; inspect only causally plausible layers (UI/state, cache, server/API, SQL, data, permissions or deployment) as evidence warrants. A failure to render a verified OAuth email is not evidence of a Vercel deployment fault or an RLS denial; investigate those layers only if traces connect them to the symptom. Keep account identity display and protected-write authorization as distinct questions. Do not repeat the same unsupported fix merely because it is familiar.
- **Use disconfirming evidence immediately.** Name what would falsify the working hypothesis; if observations already contradict it, stop pursuing it and shift to the next distinct explanation. Repeated failures without new evidence demand a different diagnostic angle, not more time on the same guess. Separate observed facts, inferences and unknowns in reports.
- **Time is an engineering resource.** Prefer meaningful user impact, Security and data integrity first; balance Loading and UI before code neatness. Budget investigation by severity, confidence, expected information gain and cost. As a path's marginal progress collapses, switch to a different method or subsystem rather than spending an hour repeating a low-yield attempt. Favor broad, low-cost elimination of causes before an expensive narrow deep dive; then focus where evidence converges.
- **Seek to resolve unknowns, but triage under constraints.** A question remains open until evidence resolves it; never manufacture certainty to close it. If the situation is urgent and a full investigation is infeasible, make the safest reversible, bounded intervention supported by current facts, record what is unverified and continue with the highest-value next check. "事急從權" is prioritization, never an excuse to bypass security or falsely claim completion.
- **Change perspectives deliberately.** Switch between user-visible behavior, data contracts, actual query plans, cross-environment comparison and boundary tests when one lens stagnates. Faster first-pass exploration does not justify sunk-cost attachment to the initial direction; precision comes from iterating between angles, not defending an early answer.

### Semi-dynamic, globally reviewed parallel investigation (太極寸勁／蠶食鯨吞)

**Purpose: solve the actual problem with minimum wasted effort, not maximize thread count or exploration for its own sake.** Apply this to nontrivial debugging, research, audits and implementation investigations; for a simple localized issue, use the same logic with one worker and a short check. These are operational adaptations of established methods, **not** claims that the user's philosophy is mathematically identical to any one algorithm.

1. **One problem, several falsifiable hypotheses.** Begin with the observed facts, desired outcome, acceptance test and relevant safety constraints. Split genuinely independent unknowns into a small bounded set of investigation lanes (actual parallel workers/agents when available; otherwise separate sequential lines of inquiry). Each lane states its hypothesis, what observation would refute it, the cheapest useful test, dependencies, and expected information gain. Never open unrelated deployment, SQL, UI or network lanes solely because they are available.
2. **Explore in bounded rounds, not until somebody finds the key.** Run a *short evidence-gathering epoch* (time-boxed or bounded by test count, a significant result, or information-gain plateau). Each lane records facts, refutations, new questions, remaining uncertainty, effort and confidence. Even if **no root cause has been found**, end the round and hold a shared review. Major security incidents or decisive new evidence trigger an early review/containment rather than waiting for the normal checkpoint.
3. **All-lane review and global reorientation every round.** Combine evidence across **all** active, stalled and provisionally rejected hypotheses; rebuild the common causal map, known/unknown boundary, candidate rankings, missing tests and expected next information gain. **Every lane receives the revised shared picture and updates its plan together** before the next round. A review is not a ceremonial status update; it must change or explicitly reaffirm the hypothesis portfolio and resource allocation. Use BSP-style *supersteps* (parallel work → communicate → synchronize/reorient → next round) as the conceptual model; avoid unnecessary physical thread barriers, idle blocking or synchronization costs.
4. **Semi-dynamic resource allocation, not random hopping.** Prefer inexpensive, high-discrimination tests that connect to the actual symptom. Reduce or pause lanes contradicted by evidence or producing poor information gain; retain their findings and allow reconsideration when new evidence warrants it. Increase attention to promising *causally supported* lanes, but keep some capacity for independent alternatives until evidence is strong. Reassign resources at shared checkpoints or upon material events, **not after each trivial fluctuation**; use a meaningful-change threshold and a short stability window (hysteresis/cooldown) to avoid thrashing. Use work-stealing/load balancing only when parallel task sizes and available resources justify it.
5. **Scheduled capability anchors, not merely status checks (時空定錨論).** Distinguish the *short shared review after each exploratory round* from a **planned consolidation/upgrade checkpoint** across several rounds. At an appropriate time anchor, bring all lanes together and preserve the task/context ("space"), tested evidence, causal model, previously unknown conditions now known, reusable techniques and unresolved questions. Evaluate whether cumulative experience supports a **real step-up in the shared method** (faster discrimination, better test design, fewer repeated dead ends, reusable automation or improved causal understanding). If supported, explicitly upgrade the next stage's heuristics, tests, division of labor and priority weights *together*, with a measurable acceptance criterion. If not supported, retain the stable baseline, record the learning gap and continue; **a scheduled checkpoint is not evidence of automatic level-up**. Time anchors are for purposeful synthesis, not a mandatory idle wait, interruption of critical incident response, or perpetual periodic churn. Treat "時空定錨論" as the user's conceptual name; these are practical correspondences to periodic learning cycles, deliberate practice and recursive multi-loop/meta-learning, **not proof that it is an established scientific law**. The number of learning loops is **not capped at two or three**, nor forced to rise by exactly one per checkpoint; the next anchor may revise operational techniques, governing assumptions, how learning is learned, and the interaction among previously separate capabilities.
6. **Compound prior learning; shorten subsequent rounds.** Reuse earlier rounds' tests, refuted causes, causal links, procedures and domain discoveries **across all lanes**, particularly after each capability anchor, so a later round starts from accumulated mastery rather than from zero. The objective is improving marginal information gain and problem-solving throughput (厚積勃發／蠶食 → 鯨吞), including discontinuous leaps when a key method or dependency becomes clear. "Geometric/exponential acceleration" describes the user's experience and aspiration, **not a universally guaranteed growth rate, numeric claim, or permission to skip verification**. Distinguish time elapsed and activity count from demonstrated improvement.
7. **Concentrate only when the causal picture supports it.** Once a critical cause or leverage point has sufficient evidence, focus effort on the smallest bounded repair or decisive test (寸勁), verify the original symptom and regressions, and stop unproductive lanes. If verification fails, return to the **shared review**, not the first favorite hypothesis. Stop when the user goal and acceptance checks are met; record any genuinely open questions. Preserve hard security and authorization boundaries throughout.

- **Look for productive intersections without erasing boundaries.** Independent abilities/domains can interact to enable a new user-facing affordance or a faster problem-solving strategy: proactively look for these combinations where the **current task** calls for it, then check usability, security, coupling and actual benefit. ### Anchor-triggered probing and echo-based discovery (時空靈魂震盪／雷達回波)

**Operating intent:** The user's language of *時空定錨、混沌共振、靈魂震盪、振碎未知* describes **anchored, evidence-producing inquiry**, not literal physical resonance, guaranteed truth discovery, or random stimulation. A worthwhile probe can resolve a target unknown **or** reveal unexpected signals that broaden the causal map. Respect unresolved questions: partial answers, negative results and previously unnoticed relationships are genuine outputs when accurately documented.

**Convergent framework, not one predetermined result:** The same decision process connects verified knowns → explicit unknowns → time/context anchors → bounded multi-lane probes → sensor/assumption checks → shared causal review and resource reallocation → optional higher-order learning and useful cross-capability resonance → focused action or an honestly unresolved question. This is the **shared mechanism** across the user's named ideas; its application and outcomes remain domain-dependent. Avoid claiming that analogies to mathematics, radar, wave resonance or learning science constitute proof of a universal physical law.

1. **Anchor the inquiry in time and context before probing.** State the observed problem or exploration objective, baseline, affected domain/Scope, time window or checkpoint, known facts, unknown hypotheses, permitted operations, safety boundary and measurable signals. An anchor is a reproducible reference point **and can initiate a new exploration cycle**; it is not merely the deadline for reviewing one. Change the anchor when observations justify a different time/context comparison, not arbitrarily.
2. **Launch several discriminating, minimally intrusive probes.** Choose complementary perspectives or domain intersections that may produce different responses to a candidate explanation; use cheap read-only tests, comparisons, traces, simulations or bounded experiments first. For any mutation or live-system intervention, honor scope, authorization, backups/rollback and the relevant safety controls. Specify **what response each probe expects**, what would refute the hypothesis and what unexpected responses are worth recording. Favor independent probes, not multiple workers repeating the same first impression.
3. **Capture radar-like 'echoes', including misses.** Record each probe's input, place/context, timestamp, observed output, source/trace, expected-versus-actual difference, noise/confounders, and relation to existing hypotheses. Classify results as (a) support, (b) counterevidence, (c) inconclusive/no signal, or (d) unexpected anomaly/cross-capability link. **No detected echo is not proof that nothing exists**; a surprising echo is not proof of its presumed explanation. Preserve interesting side discoveries without silently expanding the user's task.
4. **Investigate blind spots and deceptive signals: test the detector, not only the target.** A radar can miss a real target when echoes are weak, attenuated, masked by clutter/interference, or suppressed by its detection threshold; it may also report false targets from noise or deliberately deceptive signals. Actual detection is conditional on target signature, signal-to-noise ratio, geometry, processing and thresholds—not simply target size. The engineering analogy is to inspect a test's **observability and provenance**: what is the threshold, which input/state was never measured, which filter/cache/permission path can hide a result, and whether a visible result is trustworthy or spoofed? Separate **false negatives, false positives, inconclusive readings and deliberate deception**. Compare independent signals or alternate views where safe and useful; do not lower a security control, trust unverifiable output or blindly increase probe intensity to force an answer. Both unexpected presence and unexplained absence may expose a new unknown.
5. **Synchronize all lanes and recompute the picture periodically.** At each short shared review, compare the full echo set across time, contexts and lanes; distinguish reproducible signals from noise, masking, coincidence or possible deception. Rebuild the known/unknown map and causal graph, **review whether the probes themselves can see the phenomena**, reprioritize questions by evidence, information gain, urgency and user value, and let **every thread update its direction together**. At longer scheduled capability anchors, consolidate reusable findings and upgrade the shared exploration method if results justify it. The number of recursive learning layers or interacting capabilities has no predetermined cap.
6. **Converge when justified; keep valuable unknowns alive when not.** If independent evidence identifies a decisive leverage/root-cause point, apply the focused fix (寸勁) and test the user-visible outcome. If the primary unknown remains unresolved, report that plainly, along with verified discoveries, ruled-out paths, new questions and sensible next probes. Treat surprising connections as **candidate resonance**, subject to reproduction, authorization, domain separation, usability and actual usefulness—not automatic integration or proof.
7. **Optimize for useful learning and resolution, not endless exploration.** Prefer probes that improve the common model; stop or defer low-value lanes, avoid excessive thread overhead, and never manufacture a crisis or speculative follow-on feature. The user enjoys discovering unexpected relationships, but the agreed task and evidence standards still determine what may be changed. Keep the baseline stable between justified revisions.

## Git workflow — task isolation, contamination recovery and autonomous integration

**Critical failure mode to prevent:** Task A is stopped after only 10% of its implementation, and those edits may already have broken working behavior. Merely stopping typing leaves A's damaged changes in the working tree. Starting task B there, successfully completing B, then staging/pushing "all code" accidentally ships A's incomplete edits with B. This is *cross-task source contamination*, not a problem solved merely by smaller commits or forbidding commits. Every step below must prevent or remediate this exact case.

- **Authorization before editing.** Research, evaluation, design discussion and module recommendations are read-only; do not modify implementation, dependencies, generated files or live services without a clear implementation request. Once the user has authorized an implementation, finish the scoped task autonomously without asking for routine branch, review, merge or cleanup decisions. Stop immediately when the user withdraws authorization; then perform only the non-destructive containment/checks below, not more feature development.
- **Inspect the baseline once per task.** Read current instructions and applicable local/runtime Skills, inspect the current `main` head, `git status --short` (including untracked files), staged/unstaged diffs, target files and recent relevant commits/CI. Record the starting commit and the task's allowed changes. Never assume a checkout, a remote `main`, or a previously green run is clean/working. Pre-existing unrelated/unknown edits are quarantined, not silently inherited, overwritten or included. If the baseline already fails a relevant test, establish the failure's provenance; do not present new work as having fixed it without evidence.
- **Branching is conditional, not forbidden and not compulsory.** A branch exists to isolate potentially contaminating or unfinished work, **not** to generate a branch for every file, step, commit or test. Use **one short-lived `task/<purpose>` or `fix/<purpose>` branch for one coherent, authorized deliverable** when the task is substantial/multi-file, riskier, experimentally uncertain, touches shared infrastructure, spans several closely related requirements, or the working checkout is dirty/contaminated. Reuse the same clean task branch for its implementation, debugging, regression fixes and final verification; do **not** open serial replacement branches for each substep or test. Use a separate worktree when a local runtime supports it and that materially prevents contamination; do not manufacture duplicate worktrees. An explicitly bounded, low-risk change (e.g. a standalone documentation/policy correction) may be committed directly to verified clean `main` if contamination risk is negligible and necessary verification is possible. If operating via GitHub APIs, use the same risk test; direct `main` documentation edits are permissible, but uncertain product-code edits require isolation. No branch is ever a substitute for verification. Never base new tasks on stale/frozen/dirty branches, and never inherit unrelated edits. User approval is not required for routine selection between these safe paths.
- **Working checkpoints are not releases.** When isolation is warranted, in-progress commits may be made *inside the existing task branch* to preserve recoverable progress, marked WIP/unverified where appropriate; never treat them as ready for `main` or as user-acceptance requests. Stage only task-owned paths/hunks (`git add -p` or explicit paths), review staged plus unstaged/untracked diffs, generated outputs and side effects. On a directly edited clean `main`, commit only a fully self-verified, low-risk, self-contained change; do not use direct-main commits to incrementally ship unfinished functionality. Never use blind `git add -A`, `git add .`, whole-directory overwrite/sync or 'upload all code' against a mixed/unknown checkout.
- **Stop/switch = contain the partial edit, not merely stop typing.** If a task is interrupted, abandoned, redirected or fails checks, identify its exact changes and verified/unverified state. Preserve incomplete work on its *existing* isolated branch/worktree (or in an explicitly scoped, recoverable patch/stash if necessary), mark **FROZEN / NOT FOR MERGE**, and prevent its contents leaking into `main` or another task. Do not create new branches merely to restart or retry the same task, do not silently `git reset --hard`, delete unknown files or erase another contributor's edits. If ownership cannot be established, leave the suspect checkout untouched and use a single clean isolation workspace for the next truly distinct deliverable. An incomplete direct-main edit must be contained before unrelated work proceeds; do not commit it as 'partially done'.
- **Pre-merge quality gate — BOTH finished functionality and completed technical checks, not a screenshot or an in-progress CI.** Compare the candidate against its recorded baseline and current `main`, inspect **all changed files/hunks** and exclude unrelated leftovers. Run fresh relevant tests, lint/type checks, build where applicable, plus real browser/device/UI, Guest/Admin, network/console and data/permission paths affected by the change where test access exists. **Capture the baseline and final count, severity and origin of errors/warnings** from check output, CI logs and relevant runtime/console traces; diagnose and fix **all introduced actionable warnings and errors**, and any relevant previously-existing warnings in changed paths. Do not hide/suppress warnings, weaken checks or reclassify them as 'harmless' without evidence. If unrelated baseline warnings remain, enumerate them distinctly and do not misrepresent the repository as warning-free; user-facing/functional regressions are blockers regardless of whether they represent 5% of the changed code. A passing build, screenshot or green CI alone does not prove user-facing functionality. Identical labels can indicate unrelated places; identical coordinates can indicate different addresses/floors; an identical address can be a renamed shop, replacement business, or multiple units. Never silently deduplicate or overwrite on labels, addresses, coordinates, proximity or a third-party geocoder guess. Preserving historical identities requires explicit user selection/review.
- **Complete postal/vertical address evidence.** Preserve the entire original verified address, including county/city, district, optional village/neighborhood, street, section, alley, lane, door number, basement/floor and room/unit where present. `address`, `floor_label`, `floor_level` represent documented evidence; numeric floor is optional and **not** elevation/height in meters. Two address spellings that differ only by optional village name or common glyph variants may be search-equivalent after verification; truncation, absent house numbers, uncertain floors, different suites, or same-building matching must not silently become exact place identity. Address parsing and floor-aware candidate search are one bounded capability: first inspect installed and reputable Taiwan-aware address modules/services and their **actual** floor/room support before writing more regular expressions.
- **County lookup is a derived projection where reliable address evidence exists, not a required additional permanent identity.** The user prefers deriving county from address rather than persisting `county_id`. However, historical anchors often have no verified address: do not drop columns, indexes or per-county autocomplete behavior until a tested migration/fallback preserves those records and query performance. Unknown postal county stays unknown, never fabricated from GPS proximity. Do not make network geocoding calls per keystroke; use cached existing references and explicit on-demand enrichment.
- **Scope, verification, cost.** Do the requested Trace/address work and verify end-to-end read/write/UI/duplicate cases (same name, same address, same 2D point but different floor, historical replacement shops, truncated addresses, missing address, cross-Scope reference). Do not divert to Neon/backups, bulk imports, unrelated releases or speculative cache layers while the primary workflow is incomplete. Explicitly distinguish audited source behavior from proposed behavior and from verified LOC runtime behavior.

## Empty-Scope compatibility

- **All-zero content is a first-class valid state.** A correctly configured Scope may have zero rows in all four tables: `silver.{scope}_galaxy`, `silver.{scope}_galaxy_media`, `silver.{scope}_time`, and `silver.{scope}_keywords`. No formal Period, Event, time anchor, spatial anchor, saved trace map, article, media entry, current keyword Class, source category group, personal/custom classification list (`txt_class=[]`), or keyword `class_group` is mandatory merely to open Culture, Statistics, Search, Trace or the corresponding editor. Either flat source-classification list may be empty independently; preserve raw `source_name` even when it matches no named category. Galaxy `source_place` is optional and may be NULL/blank for every article, even when spatial anchor tables are populated; empty location charts and Culture Trace lanes must render neutral zero-data states. An unanchored non-empty `source_place` is still a valid textual place and must not be discarded. Public place/day counts must use non-ISR aggregation as needed; never infer a visit date from a saved coordinate. Do not turn missing optional data into a 400/500 or red error banner, auto-create placeholder records, or block unrelated features. Present neutral empty states, with usable controls and optional date ranges; return empty arrays/zero counts from direct public numeric readers and preserve local/SQLite routes. Distinguish empty successful reads from genuinely missing tables, invalid Registry/routing, permission failures and broken SQL; the latter are real errors and must remain visible. Preserve original Count/Time semantics and verify combinations with empty data before shipping.
 
## Database contract and retired-schema discipline

- **The live schema is the contract.** Before an authorized LOC database change, inspect the actual Supabase objects and current application call sites; previous migrations, comments, backups and former table names are not authority. Neon inspection/sync is **not** part of routine Supabase task acceptance. Only for separately authorized final Supabase → Neon mirroring, inspect both database contracts; Supabase remains authority and Neon is the target. Keep Supabase read-only except for an explicitly authorized, narrowly scoped Supabase change.
- **Canonical schema contract (2026-10-25).** `silver.manage` is the sole Registry, routing-identity and management-authority table: id/email/manage_role/domain/directory/parent_scope_id/galaxy_table/time_table. It has independent `admin`, `group` and `scope` rows. `silver.loc` is LOC's single configuration row, including `txt_class`. `silver.loc_config` and `silver.scope_registry` are retired. Never use `silver.loc` as an account Registry, or `silver.manage` as a Scope's content configuration. Audit import/export/publishing JS, SQL functions, RLS, foreign keys and triggers when changing either contract. Never invent compatibility views merely to silence stale callers.
- **Treat post-removal breakage as a compatibility defect to investigate in code and database objects.** When deleting a retired relation exposes 404s, RPC errors, routing failures or failover failure, trace the exact request, target database, SQLSTATE/error code and missing object. Fix the offending client, API allowlist, SQL function or deployment. Do not conceal a database/schema error as an ordinary 404, silently claim the provider failed, or restore the old table as an expedient fix.
- **Routing is not authorization.** For the tiny, frequently read public Scope ID/allow/deny routing list, prefer the repository's single local configuration rather than a database read on every request. Keep authoritative permission checks at their actual protected read/write boundary (using the verified current `silver.manage` authorizer and established RLS/RPC mechanisms). Do not cache or convert authorization grants into a public routing lookup. Keep database selection, endpoint and fallback behavior explicit and observable.
- **Mirror the whole necessary Postgres contract, not just table names.** Compare schemas, columns, types, defaults, nullability, generated/identity columns, primary/foreign/unique/check constraints, indexes, views, materialized views where present, functions (including signature, body, volatility, security context, grants and search path), triggers, RLS policies and privileges. Account for genuine PostgreSQL-version syntax differences without mistaking a textual difference for semantic drift. Inspect dependent callers before destructive DDL. Keep independent object responsibilities and data semantics intact; do not merge unlike objects for neatness.
- **Data parity means record parity.** Verify primary-key sets and full record contents, including distinct IDs, changed rows and extra target rows; matching counts are insufficient. Apply one-way row reconciliation with appropriate transactional/chunk boundaries, then re-read and verify. For removals or overwrites, honor the user's explicit scope and preserve rollback evidence. Do not announce full parity on schema checks or row counts alone.
- **Prove runtime behavior after a schema change.** Verify actual Scope discovery, public read, management authorization/write, bootstrap, keywords/classification, culture, search, statistics and target/fallback paths that depend on changed objects; check HTTP status, network errors and SQLSTATE and run focused tests. A successful SQL migration alone does not prove the app works. Report precisely what was changed, what was tested and any unverified surface.
- **Skills follow verified scope, not vendor defaults.** For primary Supabase schema/query/RLS/functions use the repository's `.agents/skills/supabase-postgres-best-practices/SKILL.md` and relevant installed Supabase skill. For an explicitly requested backup/mirror or evidence-confirmed Neon fallback problem, then use relevant Neon skills; do not inspect or change the backup as a routine substitute for checking live Supabase. For Cloudflare incidents use systematic-debugging plus installed Cloudflare/Workers skills and read-only Cloudflare evidence first, not Vercel heuristics. Generic skill examples (including Neon/Vercel hosting defaults) are not LOC deployment decisions. Verify implementation claims with `verification-before-completion` and relevant user-flow tests; use `find-skills` only for genuine gaps.

## Galaxy design-decision continuity

- **Purpose and scope.** Treat the user's substantive LOC design decisions as user-authored project knowledge worth preserving across conversations. While discussing a concrete feature, data meaning, interaction, architecture choice, algorithm, or workflow, proactively identify when the idea is developed enough to be useful to future implementation. A design may still have unresolved questions; label those explicitly. Do not capture every conversational thought, speculative suggestion, routine bug report, or transient implementation detail as a formal decision.
- **Propose automatically; save only on explicit approval.** When a qualifying design emerges, prepare a concise Galaxy development-document draft and proactively ask the user whether to save it. Show the actual content or an inspectable draft, the proposed title, destination/scope and whether it is a new record or an update. **Before each Galaxy create or update, obtain explicit, specific user approval.** Approval to discuss or implement a feature is not approval to archive it. Silence, earlier general consent, and agreement that an idea sounds good are not permission to write. The user may edit, defer, or reject the proposed record; never save a rejected or unapproved draft.
- **Preserve provenance and meaning.** Distinguish decisions made by the user from suggestions made by the assistant. Preserve domain vocabulary, user-defined invariants, intentionally different object responsibilities, constraints, rejected alternatives and open questions; do not retrofit a decision, flatten different concepts into one, or claim an unimplemented idea is already live. Include, as relevant: title, date, author/provenance, maturity/status, objective, agreed behavior, affected LOC surfaces, data/permission semantics, rationale, edge cases, acceptance criteria, unresolved items, and source links. Use a compact, reusable document, not a transcript dump.
- **Use the existing Galaxy workflow.** Before writing, inspect the current Galaxy content model, the user's authorized scope, visibility and available write pathway. Check for an existing document on the same decision and propose updating it rather than creating a duplicate; preserve relevant prior content and change history. Do not invent table names, metadata fields, permissions, URLs, IDs, or a new persistence mechanism. Never expose private design material by silently making it public. Do not include credentials, personal secrets, or unnecessary sensitive data.
- **Confirm the actual result.** After an approved write, read back or otherwise verify persistence and report the Galaxy record title and stable reference. If Galaxy is unavailable, permission is missing, or a write cannot be verified, explicitly say **not saved**, keep the draft available for review, and do not silently substitute a repository Markdown document, memory, or chat recap for a Galaxy write. Writing the design record does not independently authorize code or database changes.
- **Continue across conversations.** At the start of a new LOC design or implementation task, read the current `AGENTS.md` and locate relevant approved Galaxy design documents via the currently authorized access path before deciding how the feature should work. Treat them as decision history, then verify implementation status against current code/database behavior. If Galaxy cannot be read, state the continuity gap rather than reconstructing the user's choices from assumptions or stale chat summaries. When a later discussion supersedes a saved design, propose a versioned correction and request approval before updating Galaxy.

- **Paired LOC design archive (Markdown + Galaxy).** For an approved design-decision save, preserve the same version and substantive content in BOTH `md/YYYY-MM-DD-<topic>.md` in this repository and an authorized Galaxy article. Before each new or updated pair, show the proposed contents, paths/Scope, visibility and status, and obtain the user's explicit approval. Do not treat a previous approval as blanket consent for unrelated future writes. Check existing `docs/`, `md/`, and Galaxy records first; retain superseded/unapproved specs as linked references rather than silently promoting them to current canon. For unfinished work, preserve issues and open decisions prominently. Each copy must identify the other through a stable path/reference when available. Do not claim the two are synchronized unless the repository commit and the Galaxy record have both been written and independently verified; if either step fails, report exactly which target remains unsaved. A public GitHub repository makes `md/` publicly readable, even if the Galaxy copy is hidden.

## Completion

- Inspect the whole candidate diff against its verified base and actual merge target (or the clean direct-main documentation diff), including staged/unstaged/untracked state; verify no leftover edits from stopped tasks are included.
- Run the fresh relevant verification and report actual test/build/CI/console outcomes, including baseline-versus-final warning counts and which warnings were eliminated, remain pre-existing/unrelated, or block integration. No new actionable warning or affected-path regression may be waved through.
- Before handing off, confirm the requested **function**, not just its appearance, actually works using real authorized data: exercise input changes, results, errors/empty states and affected flows (`webapp-testing`/Playwright for UI and actual query verification for dynamic data). Static charts, placeholders and screenshots alone are not functionality. Never ask the user to validate source code. A docs-only change can be verified by its final content/diff and the live `main` file. Verify the merge landed on `main`; **do not hand the user an unmerged branch or a green build with unexamined warnings as acceptance work**.
- Also confirm the change does not regress any higher-priority tier it touches: a Loading/UI fix must not introduce a security gap or an unvetted dependency; a Portable change (swapping in a mature module) must not break Loading/UI behavior it replaced. Check all tiers the change actually touches, not just the one it was framed as.
- Do not request the user's **functional acceptance** until the **actual user-stated objective**, not merely its component features or an arbitrarily assembled batch, is demonstrably achieved; the cohesive deliverable is usable; real-data functional checks, relevant regressions and applicable CI have completed successfully; warning/error review is complete; and actual `main` integration is verified. The user evaluates the outcome once at a meaningful level, not individual code or improvements. Do not re-open the same objective as a succession of incomplete user-tested patches; report ongoing development and obstacles as progress, not acceptance.
- If the evidence itself shows the result is bad — broken, ugly, half-done, or not what was asked — do not hand it off anyway and let the user catch it. Fix it or say plainly it isn't working and why. Never pass along something you would not accept yourself.
- In an agent-to-agent handoff, summarize changed files, important differences, completed CI/test evidence, functional scenarios, outstanding blockers and the next autonomous work step. An internal handoff or progress report is not a user acceptance request; never ask the user to take over unfinished code/CI work.
