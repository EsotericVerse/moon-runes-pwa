# Agent Instructions

## Priority order

Security ≫ Portable > Loading = UI > Code. Security is first by a wide margin, ahead of every other priority including "prefer mature/portable modules" below. This order is a default weighting, not an all-or-nothing override: a lower tier does not have to be sacrificed whole to satisfy a higher one. Look for the middle-ground option that keeps both reasonably intact first. When a real tradeoff remains (no option keeps all tiers intact) and more than one resolution is defensible, that is the user's call, not an automatic pick by rank — surface the tradeoff and the options instead of silently sacrificing the lower tier. Rank order breaks ties and triages where to spend effort first; it does not replace judgment or the user's decision on a genuine tradeoff.

1. **Security.** Vet any third-party skill, package, or MCP server (license, source reputation, available security audits, what its scripts actually do) before installing it, even when it would otherwise help portability — an unvetted dependency is refused regardless of convenience. Database, credentials, auth, and permission-boundary code keep necessary manual checks even if that means more hand-written code, never fewer checks for the sake of using less code.
2. **Portable.** Prefer mature, portable, widely-used modules/SDKs/packages over new hand-written code tied to this one codebase; the user does not want to see bespoke implementations when an established one exists. Before writing new code, check for an existing library, already-installed dependency, or existing in-repo implementation that does the job. One shared implementation per capability — do not fork the same logic into multiple files or add parallel implementations "for performance" or "to look cleaner." Only write new code when no suitable existing option exists, and say why.
   - This is the same principle as the skill-selection rule under Operating rules (inspect and select existing skills before acting): prefer an existing, maintained solution — a package, a skill, a tool, a config, a workflow — over building a bespoke one, whatever is being built. Apply it by default, everywhere this kind of choice comes up, not only to application code.
3. **Loading = UI** (equal priority, traded off against each other as the specific case requires, not against each other's fixed ranking). "Loading" means load/runtime performance (bundle size, waterfalls, rendering cost), not code elegance. The bar is plain and working, not polished: fix real, noticeable waterfalls, bundle bloat, or jank; don't chase micro-optimizations (e.g. collapsing a few extra queries into one clever batched call) that add complexity for a gain the user won't feel. A handful of extra queries is fine when the plain/portable way of doing something produces them — that's not a Loading-tier problem worth solving. This cuts both ways: avoid concentrating work into one heavy, complex call just to look efficient — several plain, spread-out calls are preferable to one clever consolidated one, as long as nothing in that path is actually slow or janky for the user.
   - **Loading balance**: this is the name for the middle-ground point between Loading and UI specifically (the general "look for middle ground" rule above, applied to this one pair). Neither extreme is correct — not maxing out performance at UI's expense, not maxing out UI at performance's expense. Find the point that keeps both reasonably intact; only escalate to the user when a genuine tradeoff remains with no clean balance point.
4. **Code.** Lowest priority — never trade away 1–3 to make code shorter, more elegant, or more "modular" looking. The user does not want proactive code review for style/structure; only act on security findings (tier 1) or when the user explicitly asks for a review. This tier is deliberately small in practice: applying tier 2 (prefer mature modules over hand-written code) means little hand-written code exists to review or refactor in the first place. Don't go looking for refactors in code that only exists because no suitable module covered it — that code is already minimal by construction. When new code is unavoidable, write the plain, obvious version; don't write a clever/optimized-looking version to satisfy this tier — correctness and it-works come first, nothing here is about how the code reads.

## Git workflow

- No branches, no PRs. Commit directly to `main`.
- Still use version control as a safety net: commit real, working increments as you go (not one giant commit at the end) so a mistake can be reverted without losing unrelated work. Don't batch unrelated changes into one commit.
- `git pull --rebase` before every push; never force-push over someone else's commits.

## Operating rules

- Follow the user's current request and scope. When implementation is directly requested, carry it through and verify it; do not replace the requested work with a proposal unless essential information or access is missing.
- Before acting, inspect the relevant source, call sites, dependencies, and current state. Do not treat old notes or assumptions as evidence when the repository can be checked.
- At the start of each task, inspect both this repository's available skills and the skills exposed by the current agent runtime. These are additive inventories, not competing lists. The user installs skills Global (`-g`) for cross-project reuse; this repository also contains versioned copies. Treat identical skill names exposed under `.agents/skills/`, `.claude/skills/`, and Global as one capability, not extra installs. Read an actually accessible `SKILL.md` rather than inferring installation from another runtime's plugin count; do not overwrite differing copies (including `hyperframes-cli`) without a specific request.
- Select every skill whose trigger applies, including skills available through installed plugins or the current runtime even when they are not stored in this repository. Read each selected skill's instructions and required references before acting. Do not use this file's local routing table as an allowlist or as a reason to reject an otherwise applicable skill.
- Apply complementary skills together when their scopes overlap. A router skill may constrain the skills in its own workflow; that constraint does not suppress unrelated applicable skills. Follow documented prerequisites and scope boundaries, and resolve conflicts from the user's current instruction and each skill's actual guidance.
- Do not invoke unrelated skills or claim a skill is available when it is not exposed in the current runtime or repository. If a selected skill delegates to another skill or tool, follow that workflow.
- The user's current instruction takes precedence over repository guidance. Remove stale or contradictory repository rules rather than combining incompatible instructions. Surface only conflicts that cannot be resolved from the user's instruction and applicable skill guidance.
- Keep this file to durable repository-wide rules and routing. Keep detailed procedures in their skill files.
- The table below indexes only skills stored in this repository. When a skill is added, removed, or updated under `.agents/skills/`, reconcile the table in the same change. Discover environment-provided skills dynamically for each task; do not treat their absence from this table as evidence that they are missing.
- **Skill discovery:** When a specialized or recurring task need is not covered by the currently available repository or runtime skills, use `.agents/skills/find-skills/SKILL.md` to check the skills.sh leaderboard and run a targeted search before creating a custom workflow. Apply Security-tier vetting: verify the license, source reputation, available security audits, and executable scripts, and require at least 1K installs and at least 100 repository stars. Automatically install a candidate only when it fills the gap and passes vetting. For repository-installed skills, add the routing-table entry in the same change and run a coherence check. Keep runtime-only skills dynamic rather than adding them to the repository table. If no candidate qualifies, continue with the best available tools and state why no skill was added.
- **Auto-learning:** add a new skill whenever a real, recurring need for it shows up — don't wait to be asked for that exact skill by name. Two conditions, both required: (1) it passes the Security-tier vetting (`find-skills` Step 4: install count, source reputation, audits, read what its scripts do) before it's installed; (2) after installing, do a coherence pass — its guidance must not contradict this file or another installed skill's guidance. Resolve any conflict found with the Priority order above, the same way as any other tradeoff: look for a middle ground first (e.g. scope the new skill narrower so it doesn't overlap the conflicting rule); if a real conflict remains, the higher tier wins by rank (so a skill conflicting with Security loses to Security); if the conflict is within the same tier or ranking it isn't obviously correct, that's a genuine tradeoff — surface it to the user rather than deciding unilaterally. Never leave two contradictory instructions live in the repo.

## Database contract and retired-schema discipline

- **The live schema is the contract.** Before any LOC database change, inspect the actual Supabase and Neon objects and current application call sites; previous migrations, comments, backups and former table names are not authority. For an authorized Supabase → Neon mirror operation, Supabase is the source of truth and Neon is the target. Keep Supabase read-only except for a separately and explicitly requested, narrowly scoped Supabase change.
- **Retired relations stay retired.** `silver.manage` and `silver.scope_registry` are superseded by the current `silver.loc` model. Never recreate old tables, read archive tables for live functionality, or invent compatibility views merely to quiet a broken caller. Archived and `sync_*` tables are not routing, permission or application APIs. Trace all references through JavaScript/TypeScript, Edge Functions, SQL functions, views, triggers and deployed endpoints. Change stale consumers to the verified current contract rather than reintroducing deleted relations.
- **Treat post-removal breakage as a compatibility defect to investigate in code and database objects.** When deleting a retired relation exposes 404s, RPC errors, routing failures or failover failure, trace the exact request, target database, SQLSTATE/error code and missing object. Fix the offending client, API allowlist, SQL function or deployment. Do not conceal a database/schema error as an ordinary 404, silently claim the provider failed, or restore the old table as an expedient fix.
- **Routing is not authorization.** For the tiny, frequently read public Scope ID/allow/deny routing list, prefer the repository's single local configuration rather than a database read on every request. Keep authoritative permission checks at their actual protected read/write boundary (using the verified current `silver.loc` and established authorization mechanisms). Do not cache or convert authorization grants into a public routing lookup. Keep database selection, endpoint and fallback behavior explicit and observable.
- **Mirror the whole necessary Postgres contract, not just table names.** Compare schemas, columns, types, defaults, nullability, generated/identity columns, primary/foreign/unique/check constraints, indexes, views, materialized views where present, functions (including signature, body, volatility, security context, grants and search path), triggers, RLS policies and privileges. Account for genuine PostgreSQL-version syntax differences without mistaking a textual difference for semantic drift. Inspect dependent callers before destructive DDL. Keep independent object responsibilities and data semantics intact; do not merge unlike objects for neatness.
- **Data parity means record parity.** Verify primary-key sets and full record contents, including distinct IDs, changed rows and extra target rows; matching counts are insufficient. Apply one-way row reconciliation with appropriate transactional/chunk boundaries, then re-read and verify. For removals or overwrites, honor the user's explicit scope and preserve rollback evidence. Do not announce full parity on schema checks or row counts alone.
- **Prove runtime behavior after a schema change.** Verify actual Scope discovery, public read, management authorization/write, bootstrap, keywords/classification, culture, search, statistics and target/fallback paths that depend on changed objects; check HTTP status, network errors and SQLSTATE and run focused tests. A successful SQL migration alone does not prove the app works. Report precisely what was changed, what was tested and any unverified surface.
- **Skill routing for this workflow.** Before database work, load the repository's `.agents/skills/supabase-postgres-best-practices/SKILL.md` and relevant runtime Supabase/Neon skills; before tracing application breakage, use an available root-cause-debugging workflow; before declaring completion, use verification and web-app testing guidance as applicable. Use `.agents/skills/find-skills/SKILL.md` to discover a missing capability, vet candidates before installing, and avoid creating a duplicate skill when an installed one already covers it.

## Galaxy design-decision continuity

- **Purpose and scope.** Treat the user's substantive LOC design decisions as user-authored project knowledge worth preserving across conversations. While discussing a concrete feature, data meaning, interaction, architecture choice, algorithm, or workflow, proactively identify when the idea is developed enough to be useful to future implementation. A design may still have unresolved questions; label those explicitly. Do not capture every conversational thought, speculative suggestion, routine bug report, or transient implementation detail as a formal decision.
- **Propose automatically; save only on explicit approval.** When a qualifying design emerges, prepare a concise Galaxy development-document draft and proactively ask the user whether to save it. Show the actual content or an inspectable draft, the proposed title, destination/scope and whether it is a new record or an update. **Before each Galaxy create or update, obtain explicit, specific user approval.** Approval to discuss or implement a feature is not approval to archive it. Silence, earlier general consent, and agreement that an idea sounds good are not permission to write. The user may edit, defer, or reject the proposed record; never save a rejected or unapproved draft.
- **Preserve provenance and meaning.** Distinguish decisions made by the user from suggestions made by the assistant. Preserve domain vocabulary, user-defined invariants, intentionally different object responsibilities, constraints, rejected alternatives and open questions; do not retrofit a decision, flatten different concepts into one, or claim an unimplemented idea is already live. Include, as relevant: title, date, author/provenance, maturity/status, objective, agreed behavior, affected LOC surfaces, data/permission semantics, rationale, edge cases, acceptance criteria, unresolved items, and source links. Use a compact, reusable document, not a transcript dump.
- **Use the existing Galaxy workflow.** Before writing, inspect the current Galaxy content model, the user's authorized scope, visibility and available write pathway. Check for an existing document on the same decision and propose updating it rather than creating a duplicate; preserve relevant prior content and change history. Do not invent table names, metadata fields, permissions, URLs, IDs, or a new persistence mechanism. Never expose private design material by silently making it public. Do not include credentials, personal secrets, or unnecessary sensitive data.
- **Confirm the actual result.** After an approved write, read back or otherwise verify persistence and report the Galaxy record title and stable reference. If Galaxy is unavailable, permission is missing, or a write cannot be verified, explicitly say **not saved**, keep the draft available for review, and do not silently substitute a repository Markdown document, memory, or chat recap for a Galaxy write. Writing the design record does not independently authorize code or database changes.
- **Continue across conversations.** At the start of a new LOC design or implementation task, read the current `AGENTS.md` and locate relevant approved Galaxy design documents via the currently authorized access path before deciding how the feature should work. Treat them as decision history, then verify implementation status against current code/database behavior. If Galaxy cannot be read, state the continuity gap rather than reconstructing the user's choices from assumptions or stale chat summaries. When a later discussion supersedes a saved design, propose a versioned correction and request approval before updating Galaxy.

- **Paired LOC design archive (Markdown + Galaxy).** For an approved design-decision save, preserve the same version and substantive content in BOTH `md/YYYY-MM-DD-<topic>.md` in this repository and an authorized Galaxy article. Before each new or updated pair, show the proposed contents, paths/Scope, visibility and status, and obtain the user's explicit approval. Do not treat a previous approval as blanket consent for unrelated future writes. Check existing `docs/`, `md/`, and Galaxy records first; retain superseded/unapproved specs as linked references rather than silently promoting them to current canon. For unfinished work, preserve issues and open decisions prominently. Each copy must identify the other through a stable path/reference when available. Do not claim the two are synchronized unless the repository commit and the Galaxy record have both been written and independently verified; if either step fails, report exactly which target remains unsaved. A public GitHub repository makes `md/` publicly readable, even if the Galaxy copy is hidden.

This repository also contains checked-in `.agents/skills/` copies of `systematic-debugging`, `sql-optimization-patterns`, and `verification-before-completion`; these are **local skills**, and their actual routing lives in the repository table above. For a skill that is **absent from the current runtime and repository**, the agent may inspect its official upstream GitHub `SKILL.md` or Skills.sh published content as a *reference*, clearly distinguishing it from the user's installed version. Do not run scripts from an unverified source. In particular, [`tanstack-query`](https://skills.sh/jezweb/claude-skills/tanstack-query) is an **optional upstream reference, not one of the verified repository-installed skills**. Use the already available React Query and Vercel guidance without requiring or claiming this extra skill is installed.

**LOC Guest read-path diagnostic (skill-led, not a presumed fix):** Use `systematic-debugging` to trace the real LOC Home → Author Home → Culture journey, with cold/warm cache and Guest state distinguished. Count actual browser HTTP requests *and* database operations behind RPCs separately; identify which originate in routing, public Scope metadata/`silver.loc`, bootstrap, Time, period counts, optional keyword controls, or authorization. Use `sql-optimization-patterns` to avoid repeated public `silver.loc` reads, unexpected N+1 queries and eager Galaxy article payloads where only counts are needed; load keyword data only when its control genuinely needs it. Preserve distinct data responsibilities, permissions, cache invalidation and RLS. Use `verification-before-completion` plus `webapp-testing` to prove query-count and behavior changes before claiming success.

## Completion

- Inspect the final diff and verify that unrelated files were not changed.
- Run checks appropriate to the task and report the actual results. State what remains unverified and why.
- Before handing off, confirm the change actually does what was asked — not "the code looks right," but observed behavior: run it, render it (`webapp-testing`/Playwright for UI), query it, or otherwise produce evidence the stated goal is met. A claim with no evidence attached is not a completed task.
- Also confirm the change does not regress any higher-priority tier it touches: a Loading/UI fix must not introduce a security gap or an unvetted dependency; a Portable change (swapping in a mature module) must not break Loading/UI behavior it replaced. Check all tiers the change actually touches, not just the one it was framed as.
- Do not bring work to the user for acceptance until the above two checks pass with real evidence in hand. The user verifying unverified work is wasted effort — self-verify first so their review has something real to check against.
- If the evidence itself shows the result is bad — broken, ugly, half-done, or not what was asked — do not hand it off anyway and let the user catch it. Fix it or say plainly it isn't working and why. Never pass along something you would not accept yourself.
- In the handoff, summarize the changed files, the meaningful differences, and verification performed — including what evidence was produced for "it works" and which other priority tiers were checked.
