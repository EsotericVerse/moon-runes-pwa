## 現況與緊急處理

### Pre-commit syntax gate（快速、不涉及部署）
- Before any JS/JSX/TS commit or merge, run `npm run check:syntax` to parse app/scripts source files, and correct every real syntax error before delivery. This is a local check, not a demand to trigger paid deployments or automatically run GitHub Actions.
- Syntax checks detect invalid code, not Chinese/English wording, label text, historical names, or obsolete TODO semantics. Keep the GitHub Pages workflow manual-only.

### ISR operating status（更新 2026-10-27）：已啟用，僅限手動部署
- **Latest user confirmation:** ISR is **already enabled**. Do not turn it off, restart it, or treat it as a pending recovery task. This does **not** authorize automatic GitHub/Cloudflare builds, deployments, Previews, Vercel cutover, new R2/DO cache writes or paid load tests; existing manual-deployment-only cost controls remain in force. This current status supersedes dated references below saying ISR is disabled.
- Ordinary GitHub edits, branch work, tests and merges must not trigger Cloudflare deployments. Do not resume domain routing or switch on a Vercel ISR backup automatically.
- Culture, Statistics, Periods, Places, Traces and Daily Runes use the existing public DB RPC/queries and SWR/Service Worker as needed, not a mandatory ISR endpoint. Preserve lazy querying, server-side aggregate RPC, access checks and SQLite local semantics; never replace chart aggregations with repeated full-text downloads.
- Keep the current ISR/OpenNext configuration untouched. Do not add R2/DO bindings or populateRemoteCache in code and do not run a deployment to validate changes without explicit authorization. The R2 24-hour expiry rule for a retired cache prefix does not authorize new writes or deployments.
- Do not delete any Galaxy, Supabase, Neon or non-ISR storage data.

### 事急從權 — emergency restoration overrides routine process
- **Emergency is a conditional priority, not a perpetual shortcut.** If the user declares a real emergency, or evidence establishes an active serious core-function outage, material security/data-integrity failure or equivalent urgent disruption, **immediately stop all unrelated tasks and restore normal operation first**. Freeze unfinished unrelated work on its existing isolated branch; do not manufacture additional branches. Reassess and return to normal task priorities after containment. This applies to genuine urgency, not routine tweaks, minor performance tuning or ordinary feature requests.
- **Emergency code path: fastest safe correction to `main`.** Identify the smallest evidence-backed, reversible correction or rollback; perform the fastest appropriate focused checks for security, data preservation and the affected functionality; **write the emergency correction directly to a verified clean `main` immediately**, without waiting for the normal PR/branch ceremony, full CI completion, user step-by-step approval, or deployment success. A pending, failed or disabled deployment **is not a reason to withhold an otherwise safe emergency fix from `main`**. If a checkout contains another unfinished task, apply only the precise incident-owned patch against clean `main`; never include unrelated edits, force-push, bypass branch protections or ship a known unsafe guess. If no safe correction is yet established, contain the failure and investigate rather than push speculative breakage.
- **Do not confuse a Git fix with service recovery.** After the urgent `main` correction, read back its commit, complete relevant regression/CI/log checks as soon as possible, and check actual user-facing behavior in an already authorized environment. Report `main patched / live recovery not verified` until real operation is demonstrated. Never silently enable Cloudflare/ISR deployments, override credentials/RLS/write authorization, modify or destroy data, or incur unapproved production load/cost. Prioritize recovery while honoring these genuine safety/authorization boundaries.
- **No emergency branch backlog and no piecemeal user acceptance.** Close/clean any incident branch already merged; keep unfinished work `FROZEN / NOT FOR MERGE` until it can be safely finished. User acceptance remains about the integrated working experience, not branch-by-branch checks. A real emergency is the narrow exception to **when** ordinary CI/branch gates block a direct `main` correction, not an exemption from eventual verification or the feature's complete functional contract.

## 優先順序框架

Security ≫ Portable > Loading = UI > Code is the **ordinary engineering default**, not a timeless priority queue or an unconditional ordering for every task. When a real authentication, authorization, privacy, data-integrity or other security boundary is implicated, its required checks remain hard acceptance constraints; this does **not** justify elevating unrelated security or deployment work above the requested UI, product or game task. Determine the effective priority from the current context, verified severity, time pressure, likely consequences, dependencies and the user's actual objective. Preserve a workable balance among the dimensions rather than maximizing one by default. When a genuine tradeoff cannot be resolved without sacrificing an important requirement, show the alternatives and let the user decide; do not silently decide solely from the default rank.

1. **Security.** Vet any third-party skill, package, or MCP server (license, source reputation, available security audits, what its scripts actually do) before installing it, even when it would otherwise help portability — an unvetted dependency is refused regardless of convenience. Database, credentials, auth, and permission-boundary code keep necessary manual checks even if that means more hand-written code, never fewer checks for the sake of using less code.
2. **Portable.** Prefer mature, portable, widely-used modules/SDKs/packages over new hand-written code tied to this one codebase; the user does not want to see bespoke implementations when an established one exists. Before writing new code, check for an existing library, already-installed dependency, or existing in-repo implementation that does the job. One shared implementation per capability — do not fork the same logic into multiple files or add parallel implementations "for performance" or "to look cleaner." Only write new code when no suitable existing option exists, and say why.
   - This is the same principle as the skill-selection rule under Operating rules (inspect and select existing skills before acting): prefer an existing, maintained solution — a package, a skill, a tool, a config, a workflow — over building a bespoke one, whatever is being built. Apply it by default, everywhere this kind of choice comes up, not only to application code.
3. **Loading = UI** (equal priority, traded off against each other as the specific case requires, not against each other's fixed ranking). "Loading" means load/runtime performance (bundle size, waterfalls, rendering cost), not code elegance. The bar is plain and working, not polished: fix real, noticeable waterfalls, bundle bloat, or jank; don't chase micro-optimizations (e.g. collapsing a few extra queries into one clever batched call) that add complexity for a gain the user won't feel. A handful of extra queries is fine when the plain/portable way of doing something produces them — that's not a Loading-tier problem worth solving. This cuts both ways: avoid concentrating work into one heavy, complex call just to look efficient — several plain, spread-out calls are preferable to one clever consolidated one, as long as nothing in that path is actually slow or janky for the user.
   - **Loading balance**: this is the name for the middle-ground point between Loading and UI specifically (the general "look for middle ground" rule above, applied to this one pair). Neither extreme is correct — not maxing out performance at UI's expense, not maxing out UI at performance's expense. Find the point that keeps both reasonably intact; only escalate to the user when a genuine tradeoff remains with no clean balance point.
4. **Code.** Lowest priority — never trade away 1–3 to make code shorter, more elegant, or more "modular" looking. The user does not want proactive code review for style/structure; only act on security findings (tier 1) or when the user explicitly asks for a review. This tier is deliberately small in practice: applying tier 2 (prefer mature modules over hand-written code) means little hand-written code exists to review or refactor in the first place. Don't go looking for refactors in code that only exists because no suitable module covered it — that code is already minimal by construction. When new code is unavoidable, write the plain, obvious version; don't write a clever/optimized-looking version to satisfy this tier — correctness and it-works come first, nothing here is about how the code reads.

### 情境判斷：穩定框架、動態平衡
- **The framework is multi-variable, not one permanent bottom line.** Consider the specific object/domain, user intent, evidence, knowns and unknowns, time, risk, urgency, impact, dependencies, reversibility, resources and responsibility. A rule or preference expressed for one case does not automatically apply to another. Preserve each object's distinct semantics; never flatten different cases into a universal answer.
- **Use the nine-level priority spectrum as a context-dependent assessment, not a rigid task queue.** On the user's 1–9 scale, 9 is highest and 1 lowest; a normally low-priority issue can temporarily become top priority if new evidence shows urgent harm or propagation risk. A high ordinary rank does not guarantee execution ahead of incident containment or prerequisite work. Reassess as the situation changes; do not confuse this spectrum with unrelated database classification IDs.
- **Time is a decision dimension.** Compare decisions in their actual times and conditions: experience, available information, severity and consequences may change. Removing a library in one workflow and using it in another, or emphasizing Security for authorization and UI/UX for layout, is not a contradiction by itself. Investigate the changed conditions before labeling a decision inconsistent or a user changeable.
- **Treat unknowns as explicit variables, not excuses or fabricated answers.** Start from verified known facts, derive only what follows from them, and keep unresolved assumptions marked as questions until evidence narrows them. A framework can accept different variables and generate different valid decisions; its outputs are not one fixed value. Never pretend a partial observation proves an entire system.
- **Prefer stability with purposeful, bounded change.** Preserve a dependable baseline and adapt through small, justified improvements; neither freeze everything forever nor invent disruptive work to demonstrate progress. A little beneficial change is acceptable, continuous crisis and churn are not. During real emergencies, prioritize containment with the smallest safe, reversible action, then reevaluate and return to normal operating priorities once the risk subsides. Do not weaken required security checks or misstate unverified outcomes under the pretext of urgency.

### OOP 與成熟模組的使用原則
- **Security >>>>> performance.** Treat security boundaries, data integrity, and authorization as hard constraints: do not trade away a check, RLS protection, secret handling, input validation or auditability for speed, less code, or a framework feature. Guest access is intentionally public-read for published data, while write/update/delete still require their own verified authorization.
- **Why OOP exists here.** OOP is a means to improve runtime performance and safe maintainability, not a mandate to reduce object/file counts. Maintainability directly serves security: explicit ownership, localized changes, comprehensible call paths, auditable permissions, and independently verifiable behavior reduce the risk of omissions and regressions.
- **Real object boundaries first.** Preserve each Scope, Galaxy, Time, Rune, Governance, and game capability's own data semantics, responsibility, permissions, operations, and lifecycle. Consolidate only capabilities proven identical; never make unlike objects artificially identical so they can share a base class, hook, table, or API.
- **Deeply use the extensive installed module stack.** Prefer React 19 composition, state and lifecycle for UI; SWR for client-side deduplication and explicit request revalidation; Next.js 16 App Router for route rendering, published static JS snapshots and Service Worker for public metadata, and on-demand RPC for numeric reports; established visualization/editor/database SDKs for their actual responsibilities. Full article bodies used by content search stay uncached. Do not add polling or automatic focus/reconnect refetches to public database reads. Eliminate redundant custom mechanisms only after tracing callers and validating their behavior.
- **ISR is optional acceleration; core LOC functionality must not depend on it（部署鎖定見前面「現況與緊急處理」）。** With ISR disabled, expired, cold, inaccessible, slow or missing, the authorized Culture, Statistics, Periods, Places, Traces, Search, Daily Runes and editing paths must still use their independent primary **Supabase RPC/query** or applicable mobile **SQLite** reads/writes. React interaction, published static JS Blocks/Bootstrap/Config, SWR and Service Worker can each assist where useful but must not form a hidden all-or-nothing ISR chain. Numeric charts still use real aggregations and respond to filters; errors/empty states must be bounded and usable rather than hanging on a failed optional cache. Cache misses or outages must not bypass RLS, trigger uncontrolled repeated SQL, or cause huge full-article downloads. Verify the ordinary **without-ISR** user journey first, then consider a permitted optional cache only where measurable UX/cost benefit justifies its complexity.
- **Security-first acceptance.** For every nontrivial consolidation, check Guest read accessibility, protected writes, stale-data invalidation, loading/network regressions, and functional parity. A build passing is necessary but not sufficient.

## 動態判斷與除錯方法論

> 原檔用四種比喻（太極寸勁／蠶食鯨吞、時空定錨、雷達回波、多層學習）分別鋪陳同一套「證據優先、分輪調查、定期回顧」的邏輯，附帶大量學術引用。以下是去除比喻鋪陳與引用後的核心操作原則；比喻名詞只保留在括號裡供查找，不再展開說明。

**證據優先**
- 不要用記憶/第一印象判斷現況；只能拿它來決定「要先查什麼」。結論一律依當下證據（repo、provider 現況、對話紀錄）而定，不同問題查不同來源：規劃類問題查對話紀錄＋`todo.md`；程式問題查原始碼與測試；上線事故查該服務（Supabase／Cloudflare 等）當下的真實狀態。
- 第一個解釋只是假設，不是結論。先想清楚「什麼證據會推翻這個假設」，一旦證據牴觸就立刻換方向，不要重複同一個沒被支持的修法。
- 證據衝突時，以使用者最新明確說法和可重現的直接觀察為準，優先於記憶或先前的推測。

**分輪調查，而非無限鑽研（太極寸勁／蠶食鯨吞）**
- 把問題拆成幾個獨立可證偽的假設，各自訂好「用什麼最便宜的測試」「什麼結果會推翻它」。
- 探索要有時間或範圍上限（一輪），輪次結束後不論有沒有找到答案，都要回頭整合所有假設的證據，重新判斷哪些值得繼續、哪些該放棄——不是找到答案才停。
- 找到有把握的root cause後，就集中火力做最小範圍的修正並驗證，不要繼續開新的調查支線。

**定錨與探查（時空定錨／雷達回波）**
- 開始查之前先講清楚：現在的問題、基準狀態、時間範圍、已知/未知、能做什麼操作、安全邊界。
- 優先用便宜、唯讀、不影響正式環境的方式先驗證；需要變更或影響正式環境的動作才需要走授權與備份流程。
- 查不到不代表問題不存在——要分清楚「真的沒問題」「查的方法本身看不到」兩種情況，不要把「沒查到」直接當成「沒事」。
- 意外發現的線索值得記下來，但不等於證實，也不代表可以直接動手整合或改動。

**方法本身也要定期檢討（多層學習）**
- 不只是檢討「這次查到什麼」，階段性也要檢討「查的方法本身有沒有更好的做法」（怎麼測試、怎麼分配資源、怎麼回顧），但不是每輪都要升級，沒有證據支持就維持原方法。
- 不同能力/模組之間若有真的有用的組合方式可以留意並提出，但不能為了「聽起來厲害」而硬湊，也不能犧牲各自原本的職責邊界。

**先拆變數，再選方法**
- 遇到實質問題，先列出真正相關的變數（目標、時間、風險、現有證據），再決定怎麼做；舊方案是「某個情境下的結果」，不是放諸四海皆準的公式，條件變了就要重新評估。
- 規則要標明它適用的範圍與時間點，不要把一次事件或一次偏好寫成「永遠」的禁令；新指示出現時，修正舊規則本身，而不是疊加一條互相矛盾的新規則。
- 問題暫時查不清楚時，先做風險最小、可逆的處置並記下未驗證的部分，不要為了結案而瞎猜答案；事急從權也只是調整優先順序，不能拿來跳過安全檢查或假裝已完成。

## Git 工作流程：任務隔離、汙染復原與整合

**Critical failure mode to prevent:** Task A is stopped after only 10% of its implementation, and those edits may already have broken working behavior. Merely stopping typing leaves A's damaged changes in the working tree. Starting task B there, successfully completing B, then staging/pushing "all code" accidentally ships A's incomplete edits with B. This is *cross-task source contamination*, not a problem solved merely by smaller commits or forbidding commits. Every step below must prevent or remediate this exact case.

### 授權與基線
- **Authorization before editing.** Research, evaluation, design discussion and module recommendations are read-only; do not modify implementation, dependencies, generated files or live services without a clear implementation request. Once the user has authorized an implementation, finish the scoped task autonomously without asking for routine branch, review, merge or cleanup decisions. Stop immediately when the user withdraws authorization; then perform only the non-destructive containment/checks below, not more feature development.
- **Inspect the baseline once per task.** Read current instructions and applicable local/runtime Skills, inspect the current `main` head, `git status --short` (including untracked files), staged/unstaged diffs, target files and recent relevant commits/CI. Record the starting commit and the task's allowed changes. Never assume a checkout, a remote `main`, or a previously green run is clean/working. Pre-existing unrelated/unknown edits are quarantined, not silently inherited, overwritten or included. If the baseline already fails a relevant test, establish the failure's provenance; do not present new work as having fixed it without evidence.

### 分支：有條件使用，非強制也非禁止
- **Branching is conditional, not forbidden and not compulsory; emergencies use the `事急從權` direct-`main` override above.** A branch exists to isolate potentially contaminating or unfinished work, **not** to generate a branch for every file, step, commit or test. Use **one short-lived `task/<purpose>` or `fix/<purpose>` branch for one coherent, authorized deliverable** when the task is substantial/multi-file, riskier, experimentally uncertain, touches shared infrastructure, spans several closely related requirements, or the working checkout is dirty/contaminated. Reuse the same clean task branch for its implementation, debugging, regression fixes and final verification; do **not** open serial replacement branches for each substep or test. Use a separate worktree when a local runtime supports it and that materially prevents contamination; do not manufacture duplicate worktrees. An explicitly bounded, low-risk change (e.g. a standalone documentation/policy correction) may be committed directly to verified clean `main` if contamination risk is negligible and necessary verification is possible. No branch is ever a substitute for verification. Never base new tasks on stale/frozen/dirty branches, and never inherit unrelated edits. User approval is not required for routine selection between these safe paths.
- **Working checkpoints are not releases.** When isolation is warranted, in-progress commits may be made *inside the existing task branch* to preserve recoverable progress, marked WIP/unverified where appropriate; never treat them as ready for `main` or as user-acceptance requests. Stage only task-owned paths/hunks (`git add -p` or explicit paths), review staged plus unstaged/untracked diffs, generated outputs and side effects. On a directly edited clean `main`, commit only a fully self-verified, low-risk, self-contained change. Never use blind `git add -A`, `git add .`, whole-directory overwrite/sync or 'upload all code' against a mixed/unknown checkout.

### 中斷、凍結與汙染復原
- **Stop/switch = contain the partial edit, not merely stop typing.** If a task is interrupted, abandoned, redirected or fails checks, identify its exact changes and verified/unverified state. Preserve incomplete work on its *existing* isolated branch/worktree (or in an explicitly scoped, recoverable patch/stash if necessary), mark **FROZEN / NOT FOR MERGE**, and prevent its contents leaking into `main` or another task. Do not create new branches merely to restart or retry the same task, do not silently `git reset --hard`, delete unknown files or erase another contributor's edits. If ownership cannot be established, leave the suspect checkout untouched and use a single clean isolation workspace for the next truly distinct deliverable. An incomplete direct-main edit must be contained before unrelated work proceeds.

- **Mirror the whole necessary Postgres contract, not just table names.** Compare schemas, columns, types, defaults, nullability, generated/identity columns, primary/foreign/unique/check constraints, indexes, views, materialized views where present, functions (including signature, body, volatility, security context, grants and search path), triggers, RLS policies and privileges. Account for genuine PostgreSQL-version syntax differences without mistaking a textual difference for semantic drift. Inspect dependent callers before destructive DDL. Keep independent object responsibilities and data semantics intact; do not merge unlike objects for neatness.
- **Data parity means record parity.** Verify primary-key sets and full record contents, including distinct IDs, changed rows and extra target rows; matching counts are insufficient. Apply one-way row reconciliation with appropriate transactional/chunk boundaries, then re-read and verify. For removals or overwrites, honor the user's explicit scope and preserve rollback evidence. Do not announce full parity on schema checks or row counts alone.
- **Prove runtime behavior after a schema change.** Verify actual Scope discovery, public read, management authorization/write, bootstrap, keywords/classification, culture, search, statistics and target/fallback paths that depend on changed objects; check HTTP status, network errors and SQLSTATE and run focused tests. A successful SQL migration alone does not prove the app works. Report precisely what was changed, what was tested and any unverified surface.
- **Skills follow verified scope, not vendor defaults.** For primary Supabase schema/query/RLS/functions use the repository's `.agents/skills/supabase-postgres-best-practices/SKILL.md` and relevant installed Supabase skill. For an explicitly requested backup/mirror or evidence-confirmed Neon fallback problem, then use relevant Neon skills; do not inspect or change the backup as a routine substitute for checking live Supabase. For Cloudflare incidents use systematic-debugging plus installed Cloudflare/Workers skills and read-only Cloudflare evidence first, not Vercel heuristics. Generic skill examples (including Neon/Vercel hosting defaults) are not LOC deployment decisions. Verify implementation claims with `verification-before-completion` and relevant user-flow tests; use `find-skills` only for genuine gaps.

## Galaxy 設計決策存檔

- **Purpose and scope.** Treat the user's substantive LOC design decisions as user-authored project knowledge worth preserving across conversations. While discussing a concrete feature, data meaning, interaction, architecture choice, algorithm, or workflow, proactively identify when the idea is developed enough to be useful to future implementation. A design may still have unresolved questions; label those explicitly. Do not capture every conversational thought, speculative suggestion, routine bug report, or transient implementation detail as a formal decision.
- **Propose automatically; save only on explicit approval.** When a qualifying design emerges, prepare a concise Galaxy development-document draft and proactively ask the user whether to save it. Show the actual content or an inspectable draft, the proposed title, destination/scope and whether it is a new record or an update. **Before each Galaxy create or update, obtain explicit, specific user approval.** Approval to discuss or implement a feature is not approval to archive it. Silence, earlier general consent, and agreement that an idea sounds good are not permission to write. The user may edit, defer, or reject the proposed record; never save a rejected or unapproved draft.
- **Preserve provenance and meaning.** Distinguish decisions made by the user from suggestions made by the assistant. Preserve domain vocabulary, user-defined invariants, intentionally different object responsibilities, constraints, rejected alternatives and open questions; do not retrofit a decision, flatten different concepts into one, or claim an unimplemented idea is already live. Include, as relevant: title, date, author/provenance, maturity/status, objective, agreed behavior, affected LOC surfaces, data/permission semantics, rationale, edge cases, acceptance criteria, unresolved items, and source links. Use a compact, reusable document, not a transcript dump.
- **Use the existing Galaxy workflow.** Before writing, inspect the current Galaxy content model, the user's authorized scope, visibility and available write pathway. Check for an existing document on the same decision and propose updating it rather than creating a duplicate; preserve relevant prior content and change history. Do not invent table names, metadata fields, permissions, URLs, IDs, or a new persistence mechanism. Never expose private design material by silently making it public. Do not include credentials, personal secrets, or unnecessary sensitive data.
- **Confirm the actual result.** After an approved write, read back or otherwise verify persistence and report the Galaxy record title and stable reference. If Galaxy is unavailable, permission is missing, or a write cannot be verified, explicitly say **not saved**, keep the draft available for review, and do not silently substitute a repository Markdown document, memory, or chat recap for a Galaxy write. Writing the design record does not independently authorize code or database changes.
- **Continue across conversations.** At the start of a new LOC design or implementation task, read the current `AGENTS.md` and locate relevant approved Galaxy design documents via the currently authorized access path before deciding how the feature should work. Treat them as decision history, then verify implementation status against current code/database behavior. If Galaxy cannot be read, state the continuity gap rather than reconstructing the user's choices from assumptions or stale chat summaries. When a later discussion supersedes a saved design, propose a versioned correction and request approval before updating Galaxy.
- **Paired LOC design archive (Markdown + Galaxy).** For an approved design-decision save, preserve the same version and substantive content in BOTH `md/YYYY-MM-DD-<topic>.md` in this repository and an authorized Galaxy article. Before each new or updated pair, show the proposed contents, paths/Scope, visibility and status, and obtain the user's explicit approval. Do not treat a previous approval as blanket consent for unrelated future writes. Check existing `docs/`, `md/`, and Galaxy records first; retain superseded/unapproved specs as linked references rather than silently promoting them to current canon. For unfinished work, preserve issues and open decisions prominently. Each copy must identify the other through a stable path/reference when available. Do not claim the two are synchronized unless the repository commit and the Galaxy record have both been written and independently verified; if either step fails, report exactly which target remains unsaved. A public GitHub repository makes `md/` publicly readable, even if the Galaxy copy is hidden.

- Follow the user's current request and scope. Do not impose arbitrary global caps or invocation quotas; use as many nonredundant, relevant Skills as actually help the task. Evaluate overlap and conflicts before a new Skill is added; `disable-model-invocation` remains a tool-boundary signal, and an unavailable Skill never blocks an otherwise authorized task. ## 完成檢查清單

- Inspect the whole candidate diff against its verified base and actual merge target (or the clean direct-main documentation diff), including staged/unstaged/untracked state; verify no leftover edits from stopped tasks are included.
- Run focused syntax/build and behavior verification for the **changed** code and affected callers, including appropriate permission/data checks. Report actual results, new actionable warnings and unverified limitations. Do not use an untouched baseline, Chinese prose, a disabled CI workflow, or the absence of deployment as a blanket blocker.
- Before calling a feature engineering-complete, demonstrate the changed behavior with permitted local/test data and affected flows; static appearances are insufficient. For docs-only changes, verify the diff and read back `main`. Do not require the user to deploy to prove syntax, inspect code or execute unfinished tests.
- Also confirm the change does not regress any higher-priority tier it touches: a Loading/UI fix must not introduce a security gap or an unvetted dependency; a Portable change (swapping in a mature module) must not break Loading/UI behavior it replaced. Check all tiers the change actually touches, not just the one it was framed as.

- If the evidence itself shows the result is bad — broken, ugly, half-done, or not what was asked — do not hand it off anyway and let the user catch it. Fix it or say plainly it isn't working and why. Never pass along something you would not accept yourself.
- In an agent-to-agent handoff, summarize changed files, important differences, completed CI/test evidence, functional scenarios, outstanding blockers and the next autonomous work step. An internal handoff or progress report is not a user acceptance request; never ask the user to take over unfinished code/CI work.
