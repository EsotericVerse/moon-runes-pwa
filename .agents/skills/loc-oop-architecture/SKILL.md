# LOC OOP：物件利用、繼承與規則容納

本 Skill 是根目錄 [AGENTS.md](../../../AGENTS.md) 的**實作程序**，不新增與之競爭的「最高優先」禁令。授權、資料保護、Suno 入庫與決策分工以 AGENTS.md 為準；當次任務限制只在其任務範圍有效。

## 核心認知

- **OOP 以 Object 為操作與協作單位。** JavaScript 原型、`class`／`extends`、封裝、繼承、多型皆可用；React／Next.js 元件、Hooks 與服務物件可以共同構成物件導向架構，但框架本身不會讓任意 Function 集合自動成為 OOP。
- **直接用已有的部分能力就可以。** 一個物件只需兩個方法，就使用那兩個；一個現成 Function 能處理，就呼叫該 Function。無須使用整個套件的工作流，更不必為了宣稱 OOP 額外建立一串 Adapter／Wrapper／Service。
- **繼承不可被組合取代為唯一正解。** 適當的父子物件關係可繼承、覆寫與多型；物件互補時可採組合、委派、策略或介面協作。同一系統可同時存在這些關係，也可包含普通函式和自製物件。
- **規則容納後統合，而非消除差異。** 局部條件、流程、資料與權限可以不同，依需要利用配置、擴充、覆寫或局部實作協同工作。不可因相似就強制共用，也不可因有差異就完全隔離或重做全部。沒有預先指定的「模組／手工比例」或修改幅度上限。

## 任務執行程序

1. **確認需求與現況。** 讀取相關程式、安裝版本、既有 Object／Function、原生 API、擴充入口、呼叫端及規則差異。辨識「可直接使用」「可微調」「應保留獨立」「確實缺少」的能力，而不是先決定重寫或合併。
2. **按物件關係選擇實作。** 能直接呼叫既有方法就呼叫；適合繼承時繼承／覆寫；多物件協作時組合／委派；現有擴充點足夠時使用配置或插件；真正缺少時新增必要的 Function、Adapter、Hook、Wrapper 或物件。每種方法只用在能清楚解釋責任與效益的情況；不把任何一種視為預設絕對禁令。
3. **讓調整留在需要的位置。** 預設尊重現有可正常運作的物件與行為。某一規則需要改變，不表示所有物件都要變；若確實涉及跨物件契約，追查相關引用後作必要調整。確有架構性理由可以大改，但不能為了形式、檔案數或終極願景做無關修改。
4. **只共用真正相同的部分。** 可共享方法、函式、父類別、契約、服務或資料轉換；同名但不同語意的 save／delete、權限、狀態、生命週期、排序等應保留正確的責任者。必要時處理覆寫優先序、例外、錯誤及回滾，不為了共用把物件削成同型。
5. **半動態載入與物件重用。** Next.js App Router 本身可按路由分割，依真實需求決定是否預取；重型互動功能再用 `next/dynamic`、`React.lazy` 或 `import()` 延後載入。常用輕量物件／方法維持直接可用，已載入且仍有價值的實例可重用；區分模組下載／求值、物件建立、資料查詢三種成本。不要把每個 Function 都拆 Chunk、每次操作都重建實例，或把「隱藏」當作卸載。模組快取與可釋放的物件實例不可混淆。
6. **Agent 自行驗證。** 根據任務實際範圍測試共用與個別規則、操作流程、CRUD、登入權限、資料回讀、錯誤與回歸；需要時檢查 Network、chunk、建置及 CI。親自檢查所有改動與 Diff，不要求使用者 Code Review、指定實作細節或替 Agent 跑測試。僅對確實驗證的結果宣稱完成。
7. **透明交付。** 提供異動檔案與完整 Commit Diff 位置、調整理由、保留功能、測試證據及未完成事項；使用者驗收的是目標與使用體驗是否符合需求，不是替代技術品質審查。

## 長期方向與當次限制

- **高頻資料不做無謂重複解析。** JSON 是交換格式，並非每次讀取都必須重新 `JSON.parse`；應依資料特性考慮解析一次後重用、已載入 JS 常數、適當的快取，或在需要索引、篩選、更新時採 SQLite／既有 SQL 資料庫。Markdown 適合人可閱讀與編輯的內容，若需結構化使用仍會有解析成本。SQLite 不保證在所有情況比記憶體物件快，亦不應為替換 JSON 任意遷移現有資料。JS 模組快取不等於使用完自動釋放；只有無引用且可回收的物件才可能交由 GC 回收，其他資源仍須管理。
- **「未來不需要 .mjs」是終極目標，不是目前必須達成的交付條件。** JavaScript／Next.js／Node.js 本身可採不同 ESM 組織方式，是否保留 .mjs 取決於當時架構與相容性；單純把 .mjs 改名 .js、數檔案或集中 Function，均不等於完成 OOP 或模組統合。
- **現有套件是資產，不是全有全無的束縛。** 可以只利用某一 Object 的個別方法，也可以加入小幅擴充；必要的自製部分不應推翻既有可用能力。不要以「整包完整使用」或「完全不用」兩極判斷。
- **安全與授權仍有邊界。** 已交辦工程工作由 Agent 自行決定合理的實作細節；資料庫 Schema／資料、其他作品文字、部署及 Git 歷史等超出當次授權的修改，仍依 AGENTS.md 取得必要同意。Suno URL 的特定入庫另依 AGENTS.md 第三章處理。
- **任務階段不等於永久架構規則。** FAQ 暫停、符文後置、某次重構禁止資料庫寫入等，只有該任務有效。不能在新任務繼續當成絕對禁令。

**完成標準：** 在使用者授權範圍內，善用現有物件的能力、依需求保留差異並適度調整，使功能與規則正確統合；Agent 自行完成技術查證、測試及交付，不以程式形式或副檔名取代實際成果。
