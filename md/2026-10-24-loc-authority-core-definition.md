## 一、概念邊界

LOC Authority 是 LOC 的權責與信任架構，而非單一角色列表、UI 權限頁，也不是用來直接取代資料庫 RLS 的評分服務。

核心概念彼此區分：

- **Identity**：辨識個人、代理或組織身分。
- **Scope**：界定身分、資源及管理範圍與其結構關係。
- **Authority**：授權哪個身分在指定資源、範圍內執行特定操作。
- **Trust Evaluation**：提供可信程度參考；評分不代替必要的授權條件。
- **TTL／Revocation**：規定權限存續時間及撤回機制。

## 二、從身分到應用的分層

1. 外部認證層：個人可使用 OAuth（例如 Google）；企業可選擇 OIDC／SAML、AD／LDAP、SSO；SCIM 為預留佈建整合能力，非已部署聲明。
2. 身分整合層：原設計包含 Clerk 的登入流程、Session、MFA、組織與使用者管理能力。這是整合方向，必須與實際程式比對後才可標記實作完成。
3. LOC Native Identity／Scope：以持久唯一識別及 Scope ID 建立 LOC 自己的範圍識別。顯示名稱不應當成穩定授權主鍵。
4. Independent Authority／Trust：定義指定操作、資源、信任情境、跨 Scope 授權與有效期限。
5. LOC 應用層：功能模組、頁面組合及資料存取按當次有效授權提供；保留安全稽核線索。

## 三、Scope 與 Authority 不等同

Scope Tree 可以表示上下層、所屬及結構關係，**不能推論子節點自動繼承上層全部權限**。跨 Scope 的授權必須明確且獨立；同一主體持有 A Scope 權限，不代表可操作 B Scope。

讀取、編輯、管理等操作應依目標資源與授權範圍逐項定義。可視性、是否能呼叫 API、是否允許資料庫寫入也不能互相取代。

## 四、Trust 評鑑與決策

評鑑分為必要條件及可參考的風險訊號。必要身分、指定資源授權及未過期的 TTL 任一不符，不能靠高信任分數變成可執行。

可區分 **Allow**、**Step-up**（補充驗證／縮小範圍）、**Deny**。風險訊號如近期任務表現、例外行為與任務情境，僅輔助判斷，不是不可撤銷的身分證明。

授權至少要能表達主體、Scope、資源、操作、有效期限及撤銷條件。不得將模糊的信任分數當成唯一安全判準。

## 五、擴充與實作邊界

LOC Extension 可由個人、小型共享，逐步擴充至組織及企業；擴充應增添適用的政策或連接介面，而非改寫其他 Scope 的權責。LDAP、SCIM、家庭／組織與 Agent Tasks 等既有設計圖內容，並不表示目前生產環境已部署。
