## 一、真實問題：不是修改太大，而是「停手後留下殘缺」

具體事故鏈：

1. A 功能開始修改，僅完成約 10%，且已破壞原有程式碼。
2. 使用者發現未授權／錯誤修改並要求停手；Agent 只停止繼續寫程式，**沒有處理已經寫入 A 的殘缺修改**。
3. A 的那 10% 持續留在工作目錄。後續改做 B 功能，沒有先排除 A 的殘留變更。
4. B 即使完成並能正常運作，「全部 code 上傳」仍連同 A 的 10% 一起提交至 `main`。
5. 類似過程重複發生，留下的缺陷跨任務累積，產生 CI 警告與系統回歸。

**因此核心故障不是僅有「中斷」或「小步提交」，也不是 B 的品質；是跨任務工作目錄污染與無差別整批上傳。** 不應把殘缺 A 誤視為下一次 B 的合法程式碼。

## 二、已確認的設計決策

- 使用者不負責審查程式碼；過去「不開 Branch」是為了避免額外的人工審核與殘留分支，**不是反對隔離技術本身**。
- 採一功能一獨立短期 Branch；執行環境支援時搭配獨立 Worktree。Branch 是隔離工具，不是把 merge 工作交給使用者。
- Agent 自行完成需求範圍核對、修改、差異檢查、相關測試、合併與善後；不在普通開發流程中反覆要求使用者選擇。
- 功能完成、驗收並合併後，關閉 PR、刪除可清理的工作分支與 Worktree；技術權限不足無法刪除時，標記 **FROZEN／MERGED／NEVER REUSE**，後續不能以它為基礎。
- 不能為了這套流程顯著拖慢開發；快速檢查集中在任務開始、切換與合併關卡，開發中依實際影響做針對性驗證，不逐行跑完整 CI。
- 研究、找模組、討論方案並不等於授權寫程式。獲准修改後則由 Agent 一次執行到可驗收的範圍，不留半成品給下一個任務。

## 三、預防流程

### A. 任務開始

1. 讀取現行 `AGENTS.md` 與適用 Skills，核實 `main` 的當前版本、既有問題與相關測試狀態。
2. 檢查 Git 已追蹤、未追蹤、已暫存與未暫存修改；識別是否有舊工作留下的差異。
3. 由適當的基準建立**獨立 Branch／Worktree**；不可讓新 B 從 A 的未完成分支或混雜目錄開始。

### B. 進行中或被要求停手

1. 停止新增未授權的功能修改，立即核對本次改動的檔案、差異與驗證狀態。
2. 未完成、已損壞或尚未確認安全的 A 修改，僅保存在 A 的獨立分支或可追蹤的隔離補丁，標示 **FROZEN／NOT FOR MERGE**。
3. 在新 B 的工作空間排除 A 的殘留。不能確認修改歸屬時，保留嫌疑工作區、另開乾淨工作環境；不得盲目 `git reset --hard`、刪除使用者成果或把 A 一起帶走。
4. 停手不是「只停鍵盤」；**隔離與善後也是停手的一部分**，但不得藉此繼續未授權開發。

### C. 功能完成與合併

1. 比對工作分支的基準以及最新 `main`，列出實際要合併的全部檔案與差異，排除其他任務遺留的修改。
2. 僅提交所屬任務的檔案／hunk；禁止在不明混合工作目錄盲目 `git add -A`、`git add .` 或整批覆蓋上傳。
3. 針對 B 的需求與受影響的既有功能完成實際驗證；B 自己正常不代表含 A 污染的整個版本正常。
4. 由 Agent 自行處理 PR／受控合併、必要 CI 與整合後核對，再關閉／清理分支。未通過驗證的版本留在隔離環境，不合併到 `main`。

## 四、既有污染的解決流程（不只是避免再發生）

1. **確認症狀與範圍**：對具體壞掉的功能或警告，蒐集執行結果、CI 記錄、相關版本與受影響檔案；不能僅憑猜測宣布找到根因。
2. **定位 A 的殘留**：比對 `git log`、`git diff`、歷次提交與最後可用行為；若有可重現測試，必要時以 `git bisect` 縮小範圍。
3. **保留 B 的有效成果**：包括 A 與 B 同時修改同一檔案時，仍要按差異與行為判別，不能整份還原覆蓋正確修改。
4. **在獨立修復分支定向修正**：選擇性撤回殘缺 hunk 或完成必要修補，不任意改動其他功能、資料庫內容或使用者作品。
5. **重新驗證後整合**：確認原故障消失、相關功能沒有回歸，再合併與清理。若證據不足，應明確保留未解風險，而非宣稱全部修復。

## 五、現況與範圍界線（2026-10-26，使用者回報）

- 過去累積的殘缺程式碼，**使用者已透過模組清理大部分**。
- 剩餘效能問題，**使用者表示已逐步處理約九成**；這是使用者提供的進度，非此次重新測量的數據。
- 因此目前系統**相當乾淨，但尚未完全乾淨**。本決策的優先目標是**不要再繼續污染**，不是展開大規模回溯、重做既有清理或額外重構效能。
- 發現具體未解的殘缺修改時，按第四節個別追查與定向處理；沒有證據時，不假定整個 `main` 都需要回退。

## 七、簡明驗收準則

- 停手後，A 的未驗證殘缺修改不能被 B 的建置、測試或上傳意外帶入。
- 每次合併必須能指出本次所有變更的來源、所屬任務與必要驗證。
- B 的功能完成不會掩蓋 A 的殘缺；修復 A 也不會無差別撤回已正確完成的 B。
- Agent 自行完成合併與分支善後，不把程式審查負擔交給使用者，不為無意義的程序明顯犧牲開發速度。
- 文件、規則與實作狀態分開描述：**規則建立 ≠ LOC 全部歷史殘缺已修好**。
